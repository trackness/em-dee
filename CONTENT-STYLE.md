# CONTENT-STYLE.md — em-dee catalog content-design contract

This document is the content-design contract for the markdown blocks
in em-dee's embedded catalog. It captures decisions that govern
what a block says, how it says it, and where it lives in the
filesystem.

It describes the **target** schema and content rules. The catalog on
disk lags this document by design: schema restructure and finalised
block content land in subsequent PRs.

## 1. Purpose and audience

**Purpose.** Pin the design decisions that determine catalog
structure and block content so they survive across sessions and
contributors. Drafting or editing a catalog block without
consulting this contract is not licensed — open the doc, read the
relevant sections, then write.

**Direct audience.** em-dee maintainers, and Claude Code sessions
operating inside this repository when drafting or editing catalog
content.

**Transitive audience.** Downstream Claude Code sessions running
inside *other* projects whose `CLAUDE.md` was generated by em-dee.
Block content is read by those sessions as operating rules. Every
sentence in a block must be useful at that point of use — not to
em-dee's maintainers, not to a human evaluating the catalog, but
to a coding agent operating in a generated project. The maintainer
audience reads this file; the agent audience reads the rendered
blocks.

## 2. Catalog schema

The catalog lives at `internal/registry/templates/`. Three nesting
shapes are licensed.

### 2.1 Top-level cross-cutting categories

`<NN-category>/<option>.md`. The category is language-agnostic; its
content applies regardless of which language the user picked. Render
order is dictated by the folder's `NN-` prefix.

### 2.2 Language-universal per-language categories

`<lang>/<NN-category>/<option>.md`. The category applies to every
project written in that language regardless of program type. Example:
`python/20-logging/loguru.md`. Render order within a language is
dictated by the `NN-` prefix on the sub-category folder.

### 2.3 Type-conditional categories (three-level nesting)

`<lang>/<NN-type-container>/<type>/<NN-sub-category>/<option>.md`.
The container groups categories that only make sense once a program
type is chosen. Example: `python/10-type/cli/10-framework/typer.md`.

### 2.4 The container-category rule

A container folder (a non-leaf grouping like `10-type/`) is justified
only when its sub-categories are *conditional on the container's
pick*. The test is mechanical:

- `python/10-type/` qualifies. The framework options under `cli`
  (typer, click) are not the framework options under `server`
  (fastapi, django, flask). The sub-categories change as the type
  pick changes.
- `python/40-tooling/` does **not** qualify. Linter options
  (ruff, …) do not change based on any other pick. Sibling-flat at
  the language level — `python/20-linter/ruff.md` — is the right
  shape.

A container with non-conditional sub-categories is just unnecessary
nesting and should be flattened.

### 2.5 The category-design test

A category is justified when the community around a language has
multiple legitimate competing choices a project must pick from. Run
the test before adding a new category:

- Are there at least two real options projects in this language
  routinely choose between? If no, the topic belongs in `base.md`
  as language discipline.
- Is the choice forced (every project must answer) or optional?
  Either is fine; a singleton with no real pick is not.
- Would a downstream Claude Code session need to know which option
  was picked to behave correctly? If the answer is the same no
  matter what, it's not a category.

Singletons without competition belong in `base.md`, not in their own
category folder.

### 2.6 Per-language asymmetry

Per-language asymmetry is the default, not a bug. Each language gets
only the categories that pass the category-design test for *that
language*. Go's tooling space is settled, so most dev-tooling
categories simply do not exist for Go. Python's tooling space is
unsettled, so more categories are justified. Forcing symmetry across
languages to make the tree look tidy is an anti-pattern; see
section 11.

## 3. Naming and validation rules

These rules are enforced by the manifest hygiene validator. Violations
fail `task verify` loudly.

- All ids are kebab and match `^[a-z][a-z0-9-]*$`.
- Folder names are `NN-<id>`, two-digit numeric prefix plus a kebab
  id. The prefix dictates render order.
- Container folders follow the same `NN-<id>` rule.
- Option filenames are `<id>.md` matching the option id in
  `_index.yaml`.
- Language ids must not collide with top-level category ids. The
  `show` resolver depends on disambiguation; the validator enforces
  it.
- `.md` block files carry no frontmatter. Block metadata
  (`id`, `display_name`, `description`, `file`) lives in
  `_index.yaml` only.
- Block files must be non-empty. Zero-byte `.md` files are rejected.

## 4. Block content shape

Every block follows the domain-tool section template below. Order of
sections is fixed. Sections that have nothing to say are dropped, not
left as empty headings.

### 4.1 Section template

- **Default:** the chosen library / tool / pattern, plus a one-line
  rationale when the choice is non-obvious.
- A bulleted list of rules governing use — invariants, conventions,
  idioms the downstream session must follow.
- **Opt-in** / **When opted in** / **Hard constraints** sub-sections
  for any per-repo alternate that the block permits. State the
  alternate, the conditions under which it's appropriate, and the
  constraints that apply when it's chosen.
- **Excluded:** packages or patterns ruled out. Include a reason when
  the exclusion is technical (security, performance, abandonment).
  Bare names suffice when the reason is "picked one in this space."

### 4.2 Per-block targets

- 30–80 lines of rendered markdown.
- Opinionated, not encyclopedic. The block is a contract the
  downstream session follows, not a survey of the ecosystem.
- Imperative voice for rules: `Use X.`, not `You should use X.` and
  not `We use X.`.
- No marketing copy. No comparison tables against excluded options.
  If an option is excluded, name it under **Excluded** and move on.

## 5. Cross-cutting category content rules

Cross-cutting categories carry blocks whose content holds regardless
of language. Language-specific content in a cross-cutting block is
the wrong shape: it forces the downstream session to read rules that
don't apply, and it bloats the cross-cutting tree. Move the content
under the relevant language subtree instead.

Cross-cutting categories at v1:

- `20-infra/` — `docker`, `kubernetes`, `terraform`.
- `30-ci/` — `github-actions`, `gitlab-ci`.
- `40-tooling/` — `pre-commit`, `mise`, `taskfile`, `makefile`.

## 6. Foundational language discipline

Items in this section live in every language's `base.md`, not as
their own categories. They are language discipline, not pick-points.

- **Error wrapping conventions.** Idioms differ per language (Go's
  `%w` wrapping, Python's `raise ... from`); pin the language's
  idiom in `base.md`.
- **Context propagation.** Where the language has the concept (Go's
  `context.Context`, Python's `contextvars`), pin propagation rules
  in `base.md`.
- **Secret handling.** Universal principles, pinned in every
  language's `base.md`:
  - Redact at the rendering site, not the call site.
  - Source precedence: environment variables > file > flag.
  - Never log secret values, including in error messages.
  - File permissions `0600` on any secret-bearing config file.
  - No secrets in user-facing error messages.
  
  Language-specific idioms (e.g. `pydantic-settings` `SecretStr`)
  appear in the relevant category block; the principles do not move.
- **Dependency hygiene.** Manifest discipline (`go.mod`,
  `pyproject.toml`), lockfile commit policy, third-party-dep
  justification — pinned in `base.md` with language-specific manifest
  names.
- **`task verify` as the pre-commit gate.** Same load-bearing rule
  as em-dee's own `CLAUDE.md`. Pin it in every language's `base.md`
  as the required pre-commit verification step.

## 7. Python defaults

Decisions for the Python language tree. These are settled; do not
relitigate when drafting Python blocks.

- **Package manager.** `uv` is the default. `poetry` and `pip-tools`
  are alternates a project explicitly opts into. Path:
  `python/<NN>-package-manager/uv.md`, `…/poetry.md`,
  `…/pip-tools.md`.
- **Linter.** `ruff` is the default. The baseline configuration is
  `select = ["E", "F", "I", "N", "W", "UP", "B", "C4", "SIM"]`,
  `target-version = "py312"`, `line-length = 150`. Do **not** set
  `skip-magic-trailing-comma = true`. em-dee's default keeps ruff's
  default behaviour, where a trailing comma forces multi-line split.
  This diverges from the marketplace CLI baseline on exactly this
  point — call out the divergence explicitly in the linter block.
- **Type checker.** `ty` (Astral's) as default. `mypy` and `pyright`
  as alternates.
- **Testing.** `pytest`.
- **Logging.** `loguru` as default. stdlib `logging` as alternate.
  `none` is not an option for new projects.
- **Pydantic.** Foundational, lives in `python/base.md`, not as a
  category. Use pydantic for data models, period. The fastapi block
  deepens framework-specific pydantic discipline; the foundational
  rule lives in `base.md`.
- **Config parsing.** Its own category. `pydantic-settings` as
  default. `dynaconf`, `hydra`, and plain `os.environ` / `argparse`
  as alternates.
- **CI and pre-commit.** None by default. The cross-cutting `30-ci/`
  and `40-tooling/pre-commit.md` blocks exist as opt-ins.
  `python/base.md` pins `task verify` as the pre-commit gate by
  convention.

## 8. Python program types

`python/10-type/` is a container; its sub-categories are conditional
on the type pick. Options at v1:

- `cli` — invoked from a terminal by humans or agents.
- `server` — long-lived process serving HTTP.
- `library` — imported by other code, no entrypoint, governed by
  PyPI publishing patterns.
- `iac` — declarative infrastructure-as-code program; invoked by
  tooling (`pulumi up`, not directly); no main loop; tested with
  framework-specific mocks.

`tui` is **not** a Python type at v1. textual exists; the call is to
skip it until demand surfaces.

### 8.1 Conditional sub-categories per type

Type-level singleton opinions — discipline that applies to every
project of a given type with no substitute axis — live in the type's
`base.md`, not as their own single-option sub-category. The same
rule that pushes singletons out of language-level categories
(section 2.5) applies one level deeper.

- **`cli`:**
  - `base.md` — type-level CLI discipline. Includes annotation-driven
    `--yes` / `--dry-run` mutation-gating as a baked-in default
    opinion, since every CLI inherits the same gate shape and there
    is no real substitute axis. Projects downstream with no mutating
    commands delete the gating prose from their generated `CLAUDE.md`
    rather than opt in.
  - `10-framework/` — `typer` default, `click` alternate.
  - `20-consumer/` — `human`, `agent`, `mixed`. Drives the output
    contract content in the rendered block.
- **`server`:**
  - `10-framework/` — `fastapi` default, `django` and `flask` as
    alternates.
- **`library`:**
  - `base.md` — PyPI publishing, semver, public-API stability rules.
    No sub-categories at v1.
- **`iac`:**
  - `base.md` — IaC program shape: declarative graph, no main loop,
    mock pattern for tests, secrets via stack config not environment.
  - `10-framework/pulumi.md` — Pulumi-specific conventions:
    `Config(namespace).require_secret`, `Output[T]`,
    `pulumi.runtime.set_mocks` + `MockConfig` in `conftest.py`.
    Only `pulumi` is supported at v1; `cdk` and others can land
    later.

## 9. Go defaults

Go's tooling space is largely settled. `gofmt`, `golangci-lint`,
`go mod`, and `go test` are defaults pinned in `go/base.md`, not
their own categories — they fail the category-design test because
there is no real competition. Testing discipline sits in `go/base.md`
alongside them: `go test` is the only framework em-dee endorses for
new Go projects. `testify` and `ginkgo` are excluded — name them
under **Excluded** in `go/base.md`.

Go categories at v1:

- `20-logging/` — `slog` default, `zap` alternate.

Go program types under `go/10-type/`:

- `cli`
- `server`
- `tui` (bubbletea has real adoption in Go; TUI stays)
- `library`

Cobra/pflag conventions live in `go/10-type/cli/base.md`, not
`go/base.md`. The assumption only holds for the CLI type; pinning it
at language level would over-apply.

## 10. Removed languages

TS-node and Rust are removed from the catalog at v1. Re-add when
their content is real, drafted under this contract.

The validator continues to support arbitrary language ids. The
removal is a catalog content decision, not a schema change.

## 11. Anti-patterns

These are explicit prohibitions. Each fails review.

- No frontmatter in `.md` files. Metadata lives in `_index.yaml`.
- No cross-category constraint rules in code. The picker
  soft-trusts the user. Coupling-by-validation is rejected by the
  spec.
- No reordering by editing the `options:` list in `_index.yaml`.
  Change the folder's `NN-` prefix instead.
- No language-specific content in cross-cutting blocks. A
  Python-specific Dockerfile in `20-infra/` is wrong-shaped; move it
  under the language subtree.
- No forwarding-address prose for things outside the repo. A
  sentence like "the spec is gitignored but lives at …" is dead
  weight; delete the reference.
- No `spec §X` or `spec section X` citations in blocks. Those
  reference docs that are not in the repo and cannot be followed by
  the downstream session.
- No forced symmetry across languages. Each language gets only the
  categories that pass the design test for it.

## 12. Decisions deferred

Not blocking v1; flagged so future contributors do not relitigate
without context:

- Whether `cdk` (and possibly Terraform-via-CDKTF) joins
  `iac/framework/`.
- Whether a future per-type `dev/` container emerges for
  type-conditional dev tooling.
- Whether `worker` / `daemon` / `cron-job` types are worth adding.
- Whether per-category flags return via a `--config=picks.yaml`
  mechanism if scripted generation becomes a need. Per-category
  cobra flags are killed in v1.
